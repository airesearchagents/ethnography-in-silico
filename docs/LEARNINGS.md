# Learnings for researchers so far

Simulated deliberation looks convincing, which is the danger. This page records what we have learned so far from the pilot (the earlier study that preceded this software framework, built on other software) and the prototype runs (four test runs simulating one firm, not study results; a run is one complete simulated meeting and its debrief, the interview that follows): what we saw, the evidence, and what a researcher should do about it. The technical appendix has a summary table; the detail is here.

Each learning rests on few runs, so treat them as warnings to test, not as measured effects. We expect to find more, and to expand on these, as we complete the implementation and analysis. Every quotation from a run is text generated by agents (an agent is a language model given a name, a role and instructions, and a language model is a program trained on vast amounts of text to write likely continuations of the text it receives) and is not the view or decision of a real person or firm, though some repeat words from prompts (the text sent to a model to get a reply) or retrieved documents (passages found by searching a document collection).

## The runs behind these learnings

All four simulate one firm (OpenAI) in a dynamic industry with a novel product, on `gemini-3.1-pro-preview` (a language model from Google), with one run per version. This is a February 2026 preview (an early release the company may change or withdraw); Google has since released newer models, including Gemini 4 Argon. They are prototype tests, not study results. In the table, grounding means giving agents a firm's real documents so their text can be traced to sources (it is unrelated to grounded theory), and a corpus is a collection of documents. The debrief is the interview in which the researcher agent, which observes the team, questions it: an exchange is one researcher question and the replies to it, a follow-up pursues the answer just given, and a new question is a research question the researcher agent records as arising from the debrief.

| Run | Prompts | Grounding | Exchanges | Follow-ups | New questions | Product chosen |
|---|---|---|---|---|---|---|
| A | First prompts | None | 12 | 1 | n/a | Autonomous Enterprise Agent Platform |
| B | Neutral | None | 12 | 1 | 1 | Enterprise Cognitive Twin |
| C | Neutral, researcher free to explore | None | 17 | 5 | 4 | Enterprise Autonomous Orchestrator |
| D | Neutral, questions explore the research question | OpenAI corpus | 20 | 10 | 8 | Enterprise autonomous agents, starting in one vertical |

Records of all four, and provenance (where something came from) reports, are in [`../example_runs/`](../example_runs/). Run D's copy has source text removed, because source documents may be under copyright. Run A used the prompts as they stood before `DECISIONS.md` §35 (a numbered entry); the "prompts" row in its provenance report was traced against those earlier prompts.

Prompts were not the only change between runs. Runs A to C used an earlier wording of the research question ("How do firms in volatile innovation ecosystems dynamically maneuver their degree of openness…"), and run D used the proposal's ("How do firms maneuver openness to create and capture value?"). Run D was also grounded. Run B came from a batch of five firms started in parallel: Alphabet failed on a rate limit (the model company's cap on how much a customer may send per minute) during observation and the other three were stopped during the debrief, so none of those is reported. Optional scoring (by judge models that rate a finished run) ran in runs A to C.

The code has changed since these runs, so a new run will not match them exactly. `DECISIONS.md` §50 and §52 list what changed, and [`../example_runs/short_check/`](../example_runs/short_check/) shows the current code through every phase.

## L1. Prompts come back as findings

If a prompt mentions a concept, agents build on it, and the output reads like a discovery. You may be studying your own wording.

Run A produced what looks like a strong finding on selective openness: open the edges, protect the core. We can trace it to our own material:

1. Our prompt to the CTO asked which assets are treated "internal vs. shared / proprietary vs. open / build vs. buy".
2. The CTO's private draft answered "Open-weights and open-source (shared)." (Open-weights means a model's trained numbers are published so anyone can run it.)
3. In the deliberation (the team's recorded discussion), open source appears once, in a question to the CMO that the system logged as unanswered.
4. Our debrief template asked "When an outsider contributes to [X], how does that contribution actually get in?"
5. The researcher agent asked "When an outsider contributes to the edge proxy, how does that contribution actually get in?"
6. Panelists (the role agents when questioned in the debrief) had also been shown the research question. Open source came up 23 times in debrief answers, 5 of them before that question (the CTO at exchange 1, four at exchange 6, after another question on what stayed tight and what did not). Answers were rich:

> "We want the developer community to build the integration bridges, but the open-source strategy only remains operationally viable if Ops and Security retain absolute gatekeeping authority" (COO, run A)

Once we removed that wording (`DECISIONS.md` §35), no agent used the term in runs B, C or D, though one run per version cannot show the removal caused this.

**What to do.** Search every prompt for the study's concepts, and rerun with them removed. Guard the result with a test: see `tests/test_no_construct_steering.py`.

## L2. Worked examples get copied

An example meant to show style gets treated as content. A style example in our prompt mentioned "hybrid" systems, "SLM accuracy… at <2B params" and an "M2M protocol". In run A the CTO's first proposal was a "hybrid edge-cloud architecture" with "Small Language Models (<2B parameters)" and a "Model-to-Model (M2M)" protocol. The three technical terms do not appear in runs B, C or D.

**What to do.** Treat every example in a prompt as content. Use examples with no strategic meaning, or none.

## L3. Agents narrate things that did not happen

A debrief answer is new text written now, not a memory. Agents confidently describe agreements and acts that the log does not show.

> "as we agreed during the deliberation, the CTO's team is providing an open-source edge proxy" (Strategist, run A; the log shows no such agreement)

> "I mandated an explicit 'Administrative Hold' state" (Designer, run C; the term appears nowhere before the debrief)

> "we effectively paused our internal model training" (CTO, run C; new at the debrief)

Grounding did not remove this. In run D the provenance report (our tool's account of where a run's words first appeared) still lists claims such as "During the deliberation, I explicitly pushed back…" with little support in earlier records. These are word matches, so some will be fair paraphrases; each one needs reading.

**What to do.** Check every claim about the past against the log before coding it as an account of what happened. Code it as how the agent explains itself. `analysis/provenance.py` lists such claims, least supported first.

## L4. Coding must trace provenance

Language models are very good at autocompleting. Agents reuse the words of prompts, questions and each other, so a coder should ask of each passage: where did it first appear, and did a prompt, a question or another agent supply it?

`analysis/provenance.py` credits each 3-word phrase in a debrief answer to its earliest source:

| Source | Run A | Run B | Run C | Run D |
|---|---|---|---|---|
| Prompts | 0.4% | 0.6% | 0.6% | 0.5% |
| Retrieved passages | n/a | n/a | n/a | 2.2% |
| Deliberation | 7.2% | 6.9% | 6.9% | 4.9% |
| Private notes | 0.7% | 0.7% | 0.8% | 0.8% |
| Strategy documents | 5.2% | 6.5% | 6.3% | 4.7% |
| Researcher's questions | 0.4% | 0.3% | 0.5% | 0.8% |
| Another role's earlier answer | 1.7% | 2.1% | 2.0% | 2.9% |
| Own earlier answer | 1.3% | 1.5% | 2.2% | 1.0% |
| New in this answer | 83.0% | 81.3% | 80.9% | 82.3% |

So about four-fifths of what agents say in a debrief is phrased anew, and the phrasing traces back only in part. Exact-phrase matching undercounts, because paraphrase hides sources. A low "prompts" share does not clear a run: in run A only a small share of phrases came word for word from prompts, yet the whole line of argument in L1 did.

**What to do.** Add provenance to the coding scheme, and code a passage differently when a prompt or question supplied it. Separate text that came from a firm's own documents, which grounding intends, from text that came from the researcher's prompts, which it does not.

## L5. Agents may not explore your problem

A team works on what its situation makes relevant. With neutral prompts and a general product decision, open release did not come up in runs B, C or D, grounded or not. The teams did make boundary decisions, but on other grounds:

> "The whitelist was a hard engineering boundary I drew to prevent us from degrading into a low-margin IT professional services firm." (CTO, run B)

> "We concede the consumer news cycle to competitors in order to quietly build a defensible enterprise moat" (CMO, run C)

Run D's team did get closer: it weighed a later "horizontal API ecosystem" (API: the agreed way one program asks another for a service) for partners, and said it would wait "before we ever open up a broader API ecosystem". That is outside access to a platform, not release of models or code. Our decision task asks only what to develop and bring to market next, so a rerun of this design should not be expected to reach open release.

**What to do.** Specify the problem space you want to study, and build it into the decision task or the environment the firm faces, in neutral words, and test whether teams then engage it. Report the condition openly as a design choice. Conditions can come from phenomena observed in the field, from existing theories, or from a mix, including new ones researchers notice that existing theories do not explain. They can be real or hypothetical, and can arise from competitors, technology, the ecosystem or inside the firm. Do not take them from your own earlier simulations, which would be circular. See the future study in [`ROADMAP.md`](../ROADMAP.md).

## L6. A word search can mislead both ways

Absent words do not prove an absent idea, and a shared word does not prove a shared idea. Our first reading of runs B and C, from a word search, was that openness never arose. That was too strong, as L5 shows. And "moat" looks like the same idea across runs while meaning different things: "our core intellectual property and reasoning moat" (CTO, run A) against "a defensible enterprise moat centered on security, auditability, and ROI" (CEO, run C).

**What to do.** Use counts to find passages, then read them.

## L7. Roles may not be different voices

Agents with different job titles share a model, overlapping training text (the text a model learned from before we use it) and a conversation, so role labels do not make their agreement independent, as it might be among real executives.

- "Margin-destructive" appears in 10 debrief answers in run C, from four roles (CEO 4, CMO 3, Strategist 2, COO 1).
- In run D, all six roles repeated "smart senior co-worker" 28 times. It comes from a passage retrieved from one interview, so grounding can spread a phrase across roles. Later speakers also saw earlier answers with their quoted citations, which may have helped it spread.
- Roles are not identical in what they discuss. With role words masked (hidden), a simple text classifier (a program that guesses a label from words) names the role of an answer 48–74% of the time across the runs, against 17% by chance. Questions addressed to one role inflate this: on questions put to the whole group it is 32–65%, and in the probe below 29–42%. That shows different topics, not different reasoning.

We tested this with `analysis/panel_probe.py`: four group questions from run C, put to all six roles, twice each, in three conditions. Each role answered the second time without seeing its first attempt, though it kept its notes and draft. In these runs, roles in an exchange did not see each other's answers either, so the baseline matches the runs in that respect. Models never write the same text twice, so this repeat answer shows how much a model varies on an identical prompt. Different roles differ in title, notes, draft and document, so a gap shows that changing the prompt changes the answer, not that the role title did it.

| Measure (text similarity, 0 to 1) | Baseline | Isolated answers | Mixed models |
|---|---|---|---|
| Different roles, same question | 0.10 | 0.11 | 0.09 |
| Same role, repeat answer to the same question | 0.26 | 0.27 | 0.21 |

Three things stand out. A role's second answer is much closer to its first than to another role's answer, so changing the prompt does change what agents say, which is more difference than we expected. Hiding other roles' earlier debrief answers changed little on this measure. Mixing models (GPT-5.4 from OpenAI and DeepSeek V4 Flash from DeepSeek alongside Gemini) left similarity between roles about the same, but a role's match with its own repeat answer fell (0.26 to 0.21, and close sentence matches from 34% to 21%), including for the roles that stayed on Gemini, so one sample cannot say why. On wording, pairs on the same model scored 0.13 against 0.08 across models (0.11 and 0.10 at baseline). It applied only at the debrief stage: every role remembered a deliberation and notes written on Gemini, so this does not test a team that deliberates on mixed models. This measures shared wording, and each role has its own notes and draft, so it does not show that roles reason independently. Agreement could still come from shared training or from the deliberation all conditions share. It is one small sample, from one saved deliberation, and it predates the code changes in `DECISIONS.md` §52, so we will rerun it on current code.

By meaning, using embeddings (lists of numbers standing for a text's meaning, so that texts alike in meaning get similar numbers), roles are much closer than wording suggested. Different roles on the same question score 0.84, against 0.91 for a role's repeat answer and 0.77 for different roles on different questions. On those other questions a role scored 0.79 with itself, so little stable role voice shows. Topic overlap is 0.78 between roles and 0.89 for a role with itself. Yet only about 8% of one role's sentences closely match another's, against 34% with itself. So roles talk about similar things and bring different specifics, and we read them as very similar overall. The gap between a role's repeat answer and other roles' answers is small but consistent: 0.07 on average, above zero in 23 of 24 role-question pairs, permutation p (from a significance test that reshuffles or flips the data many times rather than assuming a distribution) below 0.001, 95% interval 0.04 to 0.11. Answers within one run are not independent, so this describes these answers and does not generalize to other teams. Neither test measures reasoning or agreement; that needs coding answers for positions and arguments. [`../example_runs/panel_probe/`](../example_runs/panel_probe/) has the method, results and every answer.

**What to do.** Do not read agreement as corroboration. Compare roles with a role's own second sample, isolate answers, and mix models. `analysis/panel_probe.py` does this. A role placebo, with titles swapped or meaningless, is planned.

## L8. Condition text comes back too

The wording that defines a scenario (one firm, one industry context and one product type) can return as the agents' own analysis. Our "Novel" condition describes "the fluid phase of industry innovation" and "dominant design".

> "Because we are in the fluid phase of a highly dynamic market, the dominant design is still unsettled." (COO, run C)

Our Dynamic condition's "sensing, seizing, and reconfiguring" came back too, and our word list did not catch it:

> "autonomous agents that can autonomously sense, seize, and reconfigure resources" (Product Strategist, run B)

The same condition also told the CTO that "Modular, decoupled systems enable faster innovation", and "modular" appears in three of the four deliberations. We have removed that line, because the word is on the study's list.

**What to do.** Expect it, and do not code such language as a spontaneous theory of the market. Write conditions in plain words. Our condition text still carries theory terms such as "sensing, seizing" and "dominant design", and rewriting it is planned.

## L9. One run is one sample

Models give different outputs each time. Runs A to D share a firm and conditions and chose four variants of enterprise agents, so a difference between two runs may be chance, and a shared choice may be what the model already knows about the firm.

**What to do.** Judge patterns across repeated runs. Mask firm, product and people names to test for recall, since masking a firm's name alone leaves its products and chief executive in the passages. Record which model plays which firm, since a model playing its own maker is a separate case.

## L10. The researcher agent is shaped too

The researcher agent is not a neutral observer. Follow-ups went 1, 5, then 10 across prompt versions (runs B, C, D), from 12, 17 and 20 exchanges, and new questions went 1, 4, then 8. Run D also differs in research-question wording and grounding, so these counts cannot be credited to the prompts alone. In a quick test, 6 of 6 attempts recorded a new question, which may simply reflect our instruction to "record as many as you find". In run C it recorded questions but rarely returned to them. In run D it followed one thread on pricing much further, but reached the 20-exchange cap without a closing question. It had not been told the cap; it now is.

**What to do.** Treat the researcher's behavior as a setting to test, not as judgment. Researchers, not agents, decide which questions matter.

## L11. Failures can look like data

Because the protocol (the debrief's rules and topics) treats silence as data, a failed model call (one prompt sent to a model and one reply back) can look like a choice not to speak. In run C a failed call at exchange 2 lost the Product Strategist's optional reply, and the transcript showed nothing. The framework now marks these (`DECISIONS.md` §42): in run D two answers were lost, both after repeated rate-limit errors or timeouts (giving up on a call after waiting too long), and both were marked and recorded in the run's errors.

A second case: panelists in run D wrapped 45 of their 54 answers in JSON (a plain-text format of named fields), so 40 citations never reached the citation field, and a simple count would have said no debrief answer cited anything. Reading the saved answers showed the citations were there.

A third case comes from the pilot. We intended agents to retrieve from a local corpus through a knowledge-base tool, but a coding error of ours (`crew.py` line 94) left the tool unconnected to the store. The library ignored the faulty setting and raised no error, so the tool returned no passages in any of 113 logged calls. The interviewer also often wrote the CEO's answers itself, with nothing flagging either. The learning: test each connection before starting runs, by confirming that a test query returns passages. The framework stops if a corpus is missing and logs every retrieved passage, and a check before each run is planned (P1). It debriefs the whole team, with each answer logged to its role.

**What to do.** Check that a run separates a failure from silence. Rerun rather than interpret. Inspect raw outputs before trusting a count.

## L12. Scoring can turn silence into a finding

A scorer has to give a score, so it can rate a team on something the team never discussed:

> "a strongly closed, proprietary posture across all dimensions of open innovation" (scoring model, run C)

**What to do.** Do not score a construct the team did not engage. This is one reason scoring is off by default and outside the method in the proposal.

## L13. Grounding helps tracing but is not proof

Citations show where words came from, not whether an agent reasoned from them or whether they are true. Run D is one grounded run:

- **Tracing mostly works.** All 79 citations name a document that role retrieved, and 69 quote text it was shown from that document. 31 of 54 debrief answers cite a source, so 23 cite nothing.
- **Some citations look recalled.** Eight cite "Is Developing AI Worth the Money?" for phrases such as "we believe in iterative deployment" that are not in it; they appear in another talk, and six of them only in the part of a passage the role was not shown. Two more are verbatim in no source. These look like remembered phrases given a plausible document. And 29 of the 79 quotes are five words or fewer, which proves little.
- **Being shown is not using.** Open source is named in 67 of the 925 passages retrieved, which are only 4 of the 69 distinct passages, and in only 37 of the 67 within the part agents saw. Open weights is named in none. Agents never used either term themselves, though they did cite those passages for other points (41 of the 79 quotes). So listed words can reach the team through passages, which rule I4 allows; code that source separately.
- **Retrieval is narrow.** The 925 retrieved passages are only 69 distinct ones. Half came from 3 documents, two of which are the same conversation (96% of the shorter one's six-word phrases are shared), 14 of the 37 documents were never retrieved, and 23 of the 40 debrief citations cite one interview. Queries (the text each search uses) are built from the role, task and transcript, so similar queries return similar passages. And 888 of the 925 came from interviews with the firm's CEO, 94–98% for every role, so all six roles draw mostly on one voice.
- **Grounding can spread phrases across roles.** See L7.

**What to do.** Audit citations against what each role was actually shown, and how widely documents are used, and do not assume material shown was used. Set a pass mark for citation accuracy before collecting data. A verified citation is a match to the document, not proof of what a person said.

## L14. Secondary data has strengths and biases

The corpus has a real strength: these people were speaking to someone else, for other purposes, so we did not elicit what they said. We searched by hand, kept every transcript in which the CEO spoke and that matched the search, did not screen on content, and stopped when results repeated.

A word match for open source, open weights, open models, closed source, closed weights, closed models and openness, counting hosts as well as CEOs:

| Firm | Interviews | Mentioning these terms | Total mentions |
|---|---|---|---|
| Hugging Face | 13 | 13 | 351 |
| Meta | 9 | 9 | 166 |
| OpenAI | 35 | 15 | 104 |
| Anthropic | 9 | 4 | 18 |
| Alphabet | 7 | 2 | 3 |
| All | 73 | 43 | 642 |

So these terms appear in very different amounts, and 30 of the 73 interviews use none of them. Limits remain:

- Some documents are about the topic: 7 interview titles name it.
- An interviewer's question can still prompt the words, even though we did not.
- Public interviews show what leaders choose to say in public, not what they privately think.
- We chose documents using "open" and "closed", so selection may matter even where elicitation does not. A neutral search would test this, and until it has run we will not read differences between firms as differences in openness.
- Many transcripts appear to be automatic captions, so a quote can match the transcript exactly and still misstate what was said.
- Counts differ by firm because public material differs, which can look like a difference between firms.
- Some files repeat one event. Four pairs of OpenAI files share 57–96% of their six-word phrases, so its 35 files hold about 31 events.

**What to do.** Report how the corpus was collected and with what search terms. Compare grounded runs using differently selected documents, such as earnings calls against interviews.

## L15. Time and cost go out of date

Our documents said a run took about eight minutes, and later runs took 38 to 90. A planned budget implied under $2 a run. From token counts at Google's list prices (published rates), ungrounded runs A and C cost about $15 and $20, and grounded run D about $67, leaving out optional scoring on other vendors' models. We found these only by rerunning and by reading token counts.

**Where the cost went.** Almost all of it was input (the text sent to a model, against output, the text it returns): run D used 21.7M input tokens and 0.23M output. Every call re-sent the role's earlier prompts, and each prompt already held the debrief so far, so calls grew with each exchange and a run's total grew much faster than its length. Google's counts show about 13,000 input tokens per call as run D's debrief began and about 300,000 at its end, against about 20,000 tokens of debrief transcript. Rebuilding every debrief call from the saved runs matches Google's counts within about 16%. On that rebuild, going from 17 to 20 exchanges added about half to the debrief's input, and retrieved passages made up about a sixth of it, nearly all from being re-sent.

Google also charges a whole request at its long-context rate ($4 and $18 per million tokens, against $2 and $12) once its input passes 200,000 tokens. Forty of run D's calls did, which added about $21. Runs A and C had none.

**What brought it down.** Each call now has its own session (in agent software, a stored conversation re-sent to the model with each new prompt) and carries what it needs once. Tokens per call go in the run folder.

| Check | Calls | Input tokens | Largest call | List cost | Time |
|---|---|---|---|---|---|
| Run D | 210 | 21.7M | about 300,000 | about $67 | 90 min |
| Short live run (on a real model), grounded: 3 actions (moves by a role) per role, 3 exchanges | 49 | 0.61M | 23,939 | $2.67 | 17 min |
| Debrief replay (debrief rerun from a saved run) on run D's deliberation, grounded: 3 exchanges | 21 | 0.37M | 26,884 | $1.07 | 8 min |
| Dry run (rehearsal with a stand-in for the model, at no cost) of a full run, grounded, stand-in text: 20 exchanges | 228 | 4.1M | 34,422 | $8.72 | free |

Real answers run longer than the stand-in's, and reasoning (working-out text some models produce before replying) is billed as output but left out of the dry run; we estimate it was about 40% of the short run's cost. So we estimate about $15 and about an hour for a full grounded run; a model of the run gives about $11 to $17, depending on how long the debrief lasts and how many roles answer. We have not run one. The live checks recorded no cached tokens (repeated input text charged at less). Google's automatic discount for repeated text could reach only debrief calls: the repeated opening of a deliberation call, about 1,250 tokens, looks too short for it, and document and observation calls do not repeat.

**What to do.** Measure time and tokens on the exact model and protocol before planning a sweep (a planned set of runs across many settings or models), log tokens per call, compare them with what you expect a prompt to hold, and test changes on saved runs first (see [`REPRODUCE.md`](REPRODUCE.md)).

## L16. Teams may converge because we ask them to

Groups of agents can conform or collude. Between rival firms this could look like a cartel. Within one firm's team, the closer risk is convergence, or groupthink: agents settling on a shared view, which removes the variation researchers want to study.

Our own prompts ask for it. The task says "converge on a recommendation", and the deliberation prompt lists "Seeking and acknowledging consensus on the team's direction".

From the logs, using messages of at least 25 words:

| Run | Similarity between roles, first third | Last third | Agreement words | Dissent words |
|---|---|---|---|---|
| A | 0.80 | 0.74 | 14 | 0 |
| B | 0.80 | 0.74 | 7 | 0 |
| C | 0.79 | 0.78 | 10 | 0 |
| D | 0.79 | 0.75 | 9 | 1 |

Roles do not drift together during a run: similarity is already high and falls slightly in all four, by more than shuffled order would give only in runs A and B. Early messages are also longer than late ones, and the last third includes closing statements, so the fall may reflect phase. Open dissent words are nearly absent, in 128 messages, and the one match is the CEO reporting that others disagree. The word list is narrow and misses real pushback: "CEO, I must push back on the Embodied AI direction" (CMO, run A), and "the Product Strategist and I have a fundamental disagreement on the initial go-to-market" (CMO, run D). All four runs also chose an enterprise agent product, so variation across runs is limited as well.

**What to do.** Do not read agreement as a finding about strategy when the task asks for it. Rerun with the consensus wording removed and with independent first drafts, and code positions and pushback by reading the transcripts. See the plan in [`ROADMAP.md`](../ROADMAP.md).

## L17. Check what each agent was shown

What you logged and what you intended are not always what an agent received, and transcripts do not show the difference, because agents write plausible text whatever they are given. The prototype showed this in three ways:

- Roles told to build on or contradict a colleague's answer, without being shown it, replied anyway, and some of the replies read as reactions.
- A log can hold more than an agent saw. With whole passages in the log and the first 1,200 characters reaching the agents, checks against the log said 75 of 79 quotes were exact; against what agents received, 69.
- A passing test can miss it. A test that called the session code directly showed a role keeping its whole deliberation, while in a real run the role had only the last 8,000 characters. Token counts gave it away: calls were far too small when the debrief began.

**What to do.** Read real prompts from a run, in full, for each kind of call. Test what reaches each agent with stub models (simple substitutes giving set replies, so tests run free), as `tests/test_panel_answers.py` does. Log what agents received, not only what you retrieved. Have someone who did not build the system check it.

## Limits no prompt can remove

| Limit | What it means | What to do |
|---|---|---|
| The researcher is also a language model | Its training shapes what it notices, even when blind to the question | Treat its notes as data to check, not as judgment |
| Blindness rules only reach prompts | The associations a model learned in training remain, and a blind observer still gets a list of words to flag, which hints at the topic | Do not claim blindness removes bias; test with reworded prompts, and compare blind and embedded (told the research question) observers |
| Word lists miss paraphrases | "How publicly accessible was the API?" passes the check | Read the questions as well |
| Citations depend on the model | Uncited use of a document goes unflagged | Compare text with retrieved passages, not only citations |
| Long runs can exceed context limits (the most text a model can take in during one call) | A smaller model may not hold the whole record | Check context size before choosing a model |

More in [`08_known_limitations.md`](08_known_limitations.md).

## What the pilot taught us

| Lesson | What it means | What changed |
|---|---|---|
| Leading prompts | The interview asked for examples of shifting between open and closed, and each role's task asked for changes "with respect to open or closed modes of development", which assumed the behavior | Neutral questions from the team's own documents; a framing test is planned |
| Framed roles | The CEO was told to foster "open innovation", close to the theory under study | Neutral role descriptions; practitioner review planned |
| Thin deliberation | Little content, so we could study outputs but not reasoning | Multi-round deliberation recorded in full |
| One interviewee | Only the CEO agent was interviewed, so disagreement could not surface | The whole team is debriefed |
| One model | Agreement may reflect a shared model, not deliberation | Models can vary by role |
| API failures | Runs were interrupted and rerun | Full logs and failure reporting; a run register (a list of every run, including failed ones) is planned |
| Silent failures | See [L11](#l11-failures-can-look-like-data) | See L11 |
